# 协作网关与 Pi 执行服务分离，正常对话增量下发

用户在 2026-09-29 确认采用同一工程内的两个 Bun 服务，首期均运行于本地 Mac，取代单进程建议。协作网关持有需求、会话及 MySQL 数据，不调用模型；执行服务持有活跃 Pi 会话，在代码所在机器完成模型与工具循环。正常请求只下发新消息和必要的需求变化，初始化或实例丢失时才提供初始化信息或持久化的上下文检查点；执行结果与检查点返回网关保存。该边界增加一层本机通信，但让未来网关云端化不必搬迁本机工具循环，首期无需机器调度或消息队列。增量传输不改变模型需要历史上下文的事实，也不保证 Token 节省；恢复对话不等于恢复代码或重放中断工具。

## 澄清进入开发（2026-09-29）

澄清模式按需求应用于全部会话。点击或发送“开始开发”只请求模型检查；Gateway 不再据此直接切换模式。Executor 在关联了 Gateway 的会话每轮执行前查询 `/api/conversations/:id/mode`，以返回的需求模式约束工具。网关不可用时拒绝开始该轮，不默认开放开发工具。

只有主澄清会话申请开始开发时才提供 `complete_clarification` 工具。模型按内置 grilling 全文及应用适配规则判断需求是否明确，工具返回完整结论。Gateway 仅在首次保存该轮成功结束的检查点时，将结论和开发模式在同一事务中持久化；错误或中止的轮次不放行，自动发起的下一轮开发获得开发工具。无需新增审批环节或数据库状态。该设计约束应用内的执行流程，不提供操作系统沙箱，也不替代模型对需求充分性的判断。

澄清成功的事务同时插入 `queued` 自动开发轮次，ID 固定为 `auto-<澄清轮次ID>`。网关调度后改为 `running`，沿用已有轮次状态与执行器去重机制；刷新或重复检查点不会重复创建任务，网关重启可继续派发未启动的队列。自动开发失败按普通失败轮次展示，不自动反复重试模型执行。
