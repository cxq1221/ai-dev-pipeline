# 大模型后端独立化方案

日期：2026-09-29。状态：职责选择已确认；以下实现细节为建议，待最终核对。尚未修改执行代码。

## 1. 目标与已确认选择

第三方实现共同约定的 chat 和 stop HTTP interface 后，ai_dev 即可使用该大模型后端完成整次开发执行，无需了解它使用哪种 Agent。这里的约定是项目执行协议，不声称兼容任意已有聊天协议。

- 首版同机部署，保持两个 Bun 进程，不引入远程工作区同步。
- 新会话可绑定新后端，旧会话保留原后端；不迁移不同后端之间的内部上下文。
- ai_dev 管理需求、共享工作区、Git 分支、运行预览和业务流程。
- 当前两个 module 共用 MySQL 实例，各自管理自己的表，不跨 module 直接读写内部表；第三方后端不被强制使用 MySQL。
- 大模型后端自行持久化、恢复内部会话和执行任务；ai_dev 保存可见对话、执行状态和业务结果。
- 后端内置通用工具和 Skill，首版支持外部提示词、自定义 Skill 和自定义 Tool。
- ai_dev 的业务能力通过自定义 Tool 提供，后端不内置需求更新、澄清完成或自动开发规则。
- chat 承担主要执行交互，stop 显式停止任务；断线不等于取消。

## 2. module 职责与 seam

| module | 负责 | 不负责 |
|---|---|---|
| ai_dev 需求会话 | 业务提示词、grilling、需求说明、阶段和权限选择、业务 Tool、自动开发 | 推理和工具循环、模型内部消息格式 |
| ai_dev 共享工作区 | 工作区准备、需求分支、文件与差异展示、运行预览 | 模型上下文 |
| 大模型后端 | 推理与工具循环、通用工具、扩展加载、执行约束落实、上下文和任务持久化、过程与结果输出 | 解释需求状态、直接写 ai_dev 业务表 |
| ai_dev 的 HTTP adapter | chat/stop 调用、流式事件读取、恢复连接、错误归一 | 决定需求能否开发 |

HTTP seam 隔开业务和执行。depth 应体现在调用方无需处理后端内部事件、上下文和恢复细节；locality 是业务变动集中在 ai_dev，后端差异集中在 adapter；leverage 是同一需求流程可复用不同后端。

## 3. 建议的最小 HTTP interface

以下是实现草案，不是已经存在的协议。创建会话隐含在首次 chat 中，不另设创建入口。

| 入口 | 建议语义 |
|---|---|
| `POST /chat` | 提交新执行、补交外部工具结果，或按执行标识和事件游标重连；返回流式事件 |
| `POST /stop` | 按会话和执行标识请求停止；重复停止不触发新执行 |

chat 的三种用途必须明确区分：提交消息启动新执行；提交 tool_result 继续等待中的原执行；重连只补取事件和结果。这样保持两个入口，不因工具结果或断线重试创建新的开发任务。

chat 的信息分组：

- 执行身份：会话标识、执行标识、提交消息／工具结果／重连意图、恢复游标。
- 任务内容：本轮消息、应用提示词、必要业务资料；不传后端原生历史消息。
- 执行环境：共享工作区位置、模型选择、允许使用的能力。
- 扩展：Skill 内容、自定义 Tool 的名称、描述、参数格式与执行位置。首版业务 Tool 由调用方 ai_dev 执行；后端不得把收到工具定义当成已经具备其实现。

执行返回应能表达：接收、文本、工具过程、等待外部工具结果、最终结果、成功、失败、停止。事件具有可恢复的顺序标识，ai_dev 去重落库。正常模型流结束不自动等于整个开发执行成功。

同一执行标识重试必须复用原任务；不同内容复用同一标识应报冲突。后端持久化接收后才确认，进程重启后需能查询或重连该任务；中断执行不能静默重放 Shell 或文件修改。事件或会话已经不存在时，应返回明确错误。

## 4. 自定义 Tool 与 Skill

首版不建设通用插件平台。Skill 提供执行指导；Tool 定义模型可以调用的动作，定义与实际实现分开。

| 能力 | 提供方 | 执行方式 |
|---|---|---|
| 通用工具，如读取文件、编辑、Shell | 后端内置 | 在后端执行 |
| grilling、项目规则等 Skill | ai_dev 提供内容 | 后端按本轮配置加载，不要求预装同名 Skill |
| 更新需求、提交澄清结论等自定义 Tool | ai_dev 提供定义并持有实现 | 后端返回 tool_call，ai_dev 执行后通过 chat 回传 tool_result |

业务 Tool 的一次调用流程：

1. ai_dev 在 chat 中传入工具定义，后端把它提供给模型。
2. 模型调用外部工具时，后端保存并输出带调用标识的 tool_call，等待对应结果；不自行操作业务表。
3. ai_dev 校验该会话和执行是否允许调用此工具，由业务代码执行；目标需求由 ai_dev 根据会话确定，不由模型任意指定。
4. ai_dev 用同一执行标识和工具调用标识提交 tool_result，后端继续原执行的模型与工具循环。业务失败也作为工具结果反馈。

工具等待状态需要持久化。重复事件或重复提交工具结果不能重复执行同一次业务操作；断线可恢复等待，停止后不能因迟到的工具结果重新启动执行。等待结果不算整轮成功。

内置工具不默认全部开放；ai_dev 按轮指定允许的能力，后端实际执行限制。澄清期间允许读取代码和调用必要业务 Tool，不开放 Shell 和代码写入。Skill 不能扩大工具权限。

外部配置按会话或本轮生效，不自动修改全局配置；同名能力不静默覆盖，采用清晰名称或明确替换选择。

MCP 仅作为未来可选扩展，首版不实现、不作为接入要求，也不进入本次验收范围。

## 5. 保留澄清完成与自动开发的保证

1. ai_dev 为澄清执行提供提示词、grilling、受限能力和业务 Tool。
2. 模型调用提交澄清结论时，ai_dev 保存与当前执行关联的候选结果；Tool 调用成功不立即切换阶段。
3. 后端报告该执行成功结束，ai_dev 校验候选结果与执行对应关系，再在业务事务中保存结论、改变阶段、创建唯一自动开发任务。
4. ai_dev 用新执行标识发起开发 chat，开放所需写入能力；不要求用户重复说“开始开发”。
5. 失败、停止、过期或重复事件不能推进阶段或重复启动开发。其他需求和已有普通会话仍按其所属需求的规则执行。

## 6. 数据职责与旧数据迁移

ai_dev 保留需求、可见对话、执行展示、业务状态、后端配置和会话绑定。当前后端的独立表保存原生上下文、内部任务及可恢复事件。数据库连接各自配置，表迁移各自拥有；不向后端暴露 ai_dev 业务库读写能力。

迁移现有会话时，将它们绑定到当前后端，并通过一次性迁移步骤把已有上下文导入该后端所属存储。导入要可重复执行、可核对数量，完成验证前不删除原数据。迁移是当前版本的适配工作，不要求第三方后端实现历史 Pi 导入。

停止把原生 messages 作为常规执行结果回传；常规 chat 不再由 ai_dev 读取并重送内部检查点。后端更换只影响新会话，已有后端不能在仍有绑定会话时无提示移除。

## 7. 实施顺序

1. 固定 chat/stop 与事件约定、能力限制和错误语义，形成实现方可阅读的说明。
2. 为当前后端增加自己的 MySQL 持久化和 chat/stop adapter，先保留旧调用路径用于过渡验证。
3. 将业务提示词、澄清规则和业务工具归到 ai_dev；通过业务 Tool 提供操作；工作区与预览归 ai_dev。
4. ai_dev 改用新 HTTP interface，增加会话后端绑定并迁移旧会话；验证后移除旧执行对接路径。
5. 更新 ADR-0002、配置说明和仓库指引中的数据库职责，完成真实页面验证并在空闲时更新运行进程。

不因拆分而另建薄转发 module。现有执行去重、停止、文件保护和恢复逻辑有实际 depth，应保留并重新安排归属。

## 8. 验收

- 原有需求创建、工作区、预览、多轮交流、停止和重启恢复保持可用。
- 未澄清前任何会话均不能写代码；接受推荐仍算回答；成功后自动开发且仅一次。
- 后端重启能恢复自己的会话，不依赖 ai_dev 重送原生上下文。
- chat 断线后可以补取事件，重复提交不重复执行；stop 不因重连失效。
- 自定义 Tool 提交结论后执行失败，不得进入开发。
- 自定义 Tool 可以通过 tool_call/tool_result 完成调用，重复事件不重复操作业务数据，停止后迟到结果不重启任务。
- 新会话选择不同后端后，旧会话仍发给原后端。
- 从公共 HTTP/SSE、Tool 调用、文件和浏览器 interface 验证；确定性集成测试继续只替代外部模型 HTTP。
- 当前只有一个真实后端 adapter。完整的跨实现兼容性需在第二个真实实现接入时验证，不以模拟模型或目录拆分代替证明。

这份方案不保证 AI 对需求语义的判断永远正确，也不提供操作系统级沙箱；它要求执行约束与业务状态推进由确定的程序规则执行。
