# 需求中心 MVP：可分派任务清单

关联方案：[里程碑与职责划分](plan.md)。A=产品全栈，B=AI/执行后端，C=Android/测试工程。

这些任务针对待建设的真实系统，模块路径是建议归属，不假定生产代码已经存在。前端归 `web`；需求/资料归 `requirements`；执行调度归 `executions`；Agent/Git 归 `agent`；构建归 `builds`；预览归 `runtime`；用例/结果归 `testing`。共享接口变更由主责提交，使用方共同确认。

每项实现前估到约 0.5–2 人日；超过此范围应按输入、执行、结果等具体步骤继续拆分，不能用一个“大模块完成”替代任务。下列是分派基线，不是工时承诺。

## M0：可行性与接口

- [ ] **T01：确定业务对象与执行契约** — A 主责，B/C 协作；依赖：无。
  - 交付/验收：需求与平台任务 1:1；约定执行、运行、构建、测试的 ID、状态及快照字段；各有成功/失败样例。
  - 验证：用一个需求手工串联所有样例，能够从步骤结果定位候选包与需求修订。
- [ ] **T02：Agent 真实改动验证** — B 主责；依赖：无。
  - 交付/验收：一种 Agent 能在目标仓库副本读取需求并生成真实代码差异；返回日志及失败原因。
  - 验证：对 Demo 做一个限定范围的小改动，核对实际文件差异与 Agent 输出。
- [ ] **T03：Android 构建基线** — B 主责，C 协作；依赖：无。
  - 交付/验收：固定代码提交可通过可重复命令构建 APK，并记录工具链与日志。
  - 验证：C 在目标设备安装启动该 APK；不是仅检查命令退出码。
- [ ] **T04：远程预览与输入验证** — C 主责；依赖：T03。
  - 交付/验收：网页能看到目标 Android 应用并真实点击；能够获得同一开发机的桌面入口。
  - 验证：浏览器操作使目标设备状态发生变化，断开重连后仍为同一实例。
- [ ] **T05：用例执行路径验证** — C 主责；依赖：T03。
  - 交付/验收：明确 MeterSphere 项目用例到本地/远程执行脚本的映射；回收一条通过和一条失败的步骤级结果。
  - 验证：核对脚本输入、实际断言和结果；记录当前 MeterSphere 接口能力及尚不可执行的用例。

**检查点：**有实际代码差异、可安装 APK、可操作网页预览、原始测试结果；据此重估后续周期。

## M1：持久化需求工作台

- [ ] **T06：需求创建与持久化 API** — A 主责；依赖：T01。
  - 交付/验收：保存标题、说明、优先级、备注与时间；创建需求时自动生成一个平台任务。
  - 验证：重启服务后读回原数据，重复请求不生成额外平台任务。
- [ ] **T07：需求池与详情路由接入** — A 主责；依赖：T06。
  - 交付/验收：搜索/筛选与四个详情页使用真实 API；身份与需求数据关联正确。
  - 验证：从列表进入第二条需求并刷新深链接，仍显示该需求；不同需求状态不串用。
- [ ] **T08：执行任务与事件骨架** — B 主责；依赖：T01。
  - 交付/验收：提交任务返回 runId；阶段状态及日志可订阅、可读回，重复事件不会重复推进状态。
  - 验证：模拟断线后续读事件，与服务端最终状态一致。
- [ ] **T09：Android 运行服务接口** — C 主责；依赖：T01、T04。
  - 交付/验收：提供准备、查询、停止运行实例与输入接口；所有结果包含 runtimeSessionId。
  - 验证：调用两次查询指向同一实例，停止后状态与真实进程一致。

**检查点：**创建需求并刷新继续；后台执行的状态能出现在对应需求中。

## M2：AI 辅助开发与预览

- [ ] **T10：会话、修订与需求材料** — A 主责；依赖：T06。
  - 交付/验收：多会话归属同一需求说明；消息、说明修订、截图/文件/链接引用可保存与读取。
  - 验证：切换会话不串消息；历史说明和已关联材料在刷新后仍可回看。
- [ ] **T11：执行快照与 Agent 上下文** — B 主责；依赖：T02、T08、T10。
  - 交付/验收：启动时固定需求修订、材料引用、仓库和代码输入；运行期间新增消息不悄悄修改执行输入。
  - 验证：执行中修改需求，完成记录仍引用原快照，下次执行引用新修订。
- [ ] **T12：工作区与实际差异结果** — B 主责；依赖：T11。
  - 交付/验收：按需求隔离工作区；Agent 修改后输出真实 diff、开发验证结果与日志。
  - 验证：两个需求的文件变动互不污染；失败执行保留输入和日志。
- [ ] **T13：确认具体差异并提交** — B 主责，A 接入 UI；依赖：T12。
  - 交付/验收：用户确认实际 diff 后生成提交；确认前差异再次变化时重新展示待确认内容。
  - 验证：提交 SHA 对应的内容与确认内容一致，重复点击不重复创建提交。
- [ ] **T14：共享预览与多窗口** — C 主责；依赖：T09。
  - 交付/验收：应用、小窗、新页面、桌面使用同一运行会话；人和 AI 都能操作，不增加接管流程。
  - 验证：在两个入口操作，页面变化相互可见；关闭其中一个窗口不误停实例。
- [ ] **T15：Android 重新加载流程** — C 主责，B 提供构建能力；依赖：T03、T12、T14。
  - 交付/验收：重新加载会编译指定工作区快照、安装并启动；失败时显示日志及仍在运行的代码标识。
  - 验证：修改一个可见文案后重新加载，确认设备显示新内容；编译失败不能显示新代码已运行。
- [ ] **T16：开发页面全链路接入** — A 主责；依赖：T08、T10–T15。
  - 交付/验收：讨论/开发、真实修改建议、确认提交、预览操作与状态联通。
  - 验证：从新建需求走到设备上看到实际改动，并回到页面核对提交。

**检查点：**一个真实需求完成“讨论 → 改代码 → 操作预览 → 确认提交”；不是预设文案切换。

## M3：候选包与文档

- [ ] **T17：固定提交的分阶段构建** — B 主责；依赖：T03、T08、T13。
  - 交付/验收：SDK、Demo、文档阶段分别记录状态、日志和输出；执行期间代码输入保持不变。
  - 验证：触发构建后继续修改工作区，已触发构建仍产出原提交对应的内容。
- [ ] **T18：构建输出存储与清单** — B 主责，A 提供存储能力；依赖：T17。
  - 交付/验收：保存 APK/AAR/文档与文件摘要；结果包含 buildId、commitSHA、输出引用。
  - 验证：下载后核对摘要并在目标设备安装；文档入口对应这次构建。
- [ ] **T19：需求内制品页面接入** — A 主责；依赖：T18。
  - 交付/验收：展示阶段进度、历史候选包、下载/体验/文档入口以及对应测试记录。
  - 验证：回看旧候选包不会跳到最新包，未生成的输出没有可用下载入口。
- [ ] **T20：构建失败与重试记录** — B 主责；依赖：T17。
  - 交付/验收：超时/取消/阶段失败有明确终态；重试保留前次记录与输入。
  - 验证：制造编译失败后修复并重试，前后日志、提交及输出仍分别可查。

**检查点：**从需求下载的 APK 可以真实安装；SDK 与文档输出可追溯到同一提交。

## M4：系统测试与报告

- [ ] **T21：可执行用例集配置与快照** — C 主责；依赖：T01、T05。
  - 交付/验收：约定 suite/case 与执行脚本的映射，配置环境与设备；保留 MeterSphere 项目入口和用例来源。
  - 验证：逐条核对首批核心用例能执行，缺少脚本的用例不会被误报为通过。
- [ ] **T22：针对候选包启动系统测试** — C 主责，B 提供调度；依赖：T08、T18、T21。
  - 交付/验收：绑定制品摘要、用例快照与环境设备；测试运行资源与交互预览隔离。
  - 验证：运行中编辑用例配置或切换预览，正在执行的测试输入不变。
- [ ] **T23：原始用例、步骤与证据采集** — C 主责；依赖：T22。
  - 交付/验收：保存输入/预期/实际、状态、日志与截图引用；保留失败和后续重试。
  - 验证：故意让一个断言失败，能定位到具体步骤；设备故障与业务断言失败可区分。
- [ ] **T24：基于原始结果生成 AI 报告** — B 主责，C 定义结果规范；依赖：T23。
  - 交付/验收：汇总覆盖、问题和建议并引用原始用例/步骤；生成失败不影响原始报告。
  - 验证：对通过、失败、阻塞、跳过与缺证据样例核对结论；断开模型连接仍能查看原始结果。
- [ ] **T25：测试入口与详细报告页面** — A 主责；依赖：T21–T24。
  - 交付/验收：选择候选包/用例集/环境/设备，查看测试概览、AI 总结及可切换的用例步骤。
  - 验证：同一需求两次测试的概览、步骤和证据分别正确；复制报告链接后可直接进入。

**检查点：**真实用例执行、逐步骤结果与 AI 报告完整；未执行/缺证据不能被总结为成功。

## M5：内部试用

- [ ] **T26：后台任务恢复与取消** — B 主责；依赖：T20、T22。
  - 交付/验收：执行进程中断后能查询/恢复或明确结束；取消/重复回调不产生重复输出或永久运行中状态。
  - 验证：中断 Worker 后重启，检查任务、制品与报告的一致性。
- [ ] **T27：页面刷新、失联与失败体验** — A 主责；依赖：T16、T19、T25。
  - 交付/验收：刷新后恢复当前需求、运行状态和历史记录；错误提示指向对应日志或可执行操作。
  - 验证：刷新需求、候选包和报告深链接，依次检查内容归属。
- [ ] **T28：并发与设备稳定性检查** — C 主责；依赖：T15、T23、T26。
  - 交付/验收：两个需求的预览/测试互不污染；资源不足时排队，结束后释放资源。
  - 验证：并行执行两个不同需求、主动断开设备，再检查实例与测试记录。
- [ ] **T29：三个真实需求试用与复盘** — A 组织，B/C 对各自能力负责；依赖：T26–T28。
  - 交付/验收：覆盖正常完成、失败修改复测、中断恢复；记录成功率、耗时、人工修复次数及失败原因。
  - 验证：逐条演示，并按原始记录复核；将剩余问题按是否阻断首期目标排序。

**检查点：**具备可重复的真实闭环、可解释的失败和可持续回看的历史；由用户决定下一阶段投入。
