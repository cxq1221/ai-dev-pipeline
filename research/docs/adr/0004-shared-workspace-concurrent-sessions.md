# 同一需求的多个会话可同时修改持久共享工作区

2026-09-23 第二轮架构访谈中，用户明确一个需求对应一个持久工作区和需求分支，所有会话共享代码与预览、保留各自上下文，并且不限制同时修改。该决定取代“同一工作区一次只有一个写代码执行”的原建议，以及旧词汇表中“主执行 Agent 唯一可写”的约束。

平台不能把开发执行在需求级串行化，也不以每会话长期独立分支替代共享代码。不同会话可以同时产出并应用修改；一个会话的模型上下文可能落后于其他会话，必须能观察共同代码发生的变化。

第三轮用户选择冲突处理按推荐：保留已发布的修改，由后一执行重新读取并协调冲突；只重试冲突操作，不使整个需求串行，也不静默覆盖。同一需求的短时原子发布与 Git 引用更新属于数据一致性措施，不是开发执行排队。

用户同时选择提交由 AI 自主决策，不增加人工确认前置。提交范围必须形成明确的代码快照并保留来源；已提交内容不会因后续会话修改而变化。撤销也必须是检查当前基线的反向修改，不能恢复整个旧目录而抹掉其他会话工作。
